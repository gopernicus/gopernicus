## Goal

Each issue closes with one small PR a host can adopt independently: an actionable, distinct identity error
that stops the relay instead of spamming it; a default integrity policy built from the model that is a
no-op on types without `owner`, and a loud boot when a host leaves an unscoped rule against a model that
cannot satisfy it; and a `BeforeErase` hook so one erase request does the authorization cleanup
server-side for every client, with a written idempotent-repair story.

## Definition of Done

- `errors.Is(err, tuplecache.ErrSourceIdentity)` and `errors.Is(err, tuplecache.ErrUnavailable)` are both
  true for an identity mismatch on pgx and turso, from `Snapshot` and from `Acknowledge`; under
  `workers.Pool` the relay logs the cause and "restart the process" at ERROR exactly once, the pool stops and
  `Run` returns an error satisfying `errors.Is(_, ErrSourceIdentity)`; `Stats().Detached` is true; decisions
  fall back to SQL.
- `mutations.DefaultIntegrityPolicyFor(model)` yields one explicit `owner` rule per modelled type that
  declares `owner`; `authorization.New` refuses (R-1) an unscoped rule whose relation some modelled type with
  relations does not declare, naming the types and the two fixes; gps-three-sixty can run
  `DefaultIntegrityPolicyFor(Model())` plus its platform-admin rule.
- `AdministrationConfig.BeforeErase` runs after the pocket's own checks and before the store transaction; a
  non-nil error refuses the erase with nothing erased and the route maps it by its sdk kind; a re-run
  completes a half-finished erase; auth-cms and production-baseline wire a hook that revokes the target's
  role assignments in every scope with the administrator as audit actor, and both show the refusal path.
- Every PR: `make guard && make check` green; the live bite-proofs run under `make test-stores`; tags cut per
  the release plan after a green `live-stores` dispatch on `main`, confirmed on origin, cold-verified.
- One `RELEASING.md` record with host upgrade notes; gps-three-sixty's browser-side erase sequence has a
  server-side replacement it can delete.

## Out of scope

- A generic "repeat identical error" log dampener in `sdk/pkg/workers`. The relay's identity failure is
  terminal, so the right behaviour is to stop, not to throttle; a pool-level dampener is a separate sdk ask.
- Re-binding the relay to a new source identity without a restart. The binding (protocol, schema, identity,
  freshness) is fixed at construction by design (`pgx/tuple_cache.go:91`, `runtime.go:122`).
- A `PurgeSubjectAuthorization` command across every scope. `TargetSubject` purges global-scope tuples only
  (`mutations/mutation.go:48-56`); resource-scoped tuples such as `platform:global#admin@user:x` need a
  per-assignment unassign, which the hook does with the pocket's existing audited commands.
- A read-only pre-check for the accepting-claim refusal before the hook runs (it would need a new
  repository port; the re-run repairs state (b) instead — see Design #256.5).
- A startup refusal or posture finding when `UserErasureRoute` is on without a hook (#256 option 3). The
  authentication pocket cannot know a host uses authorization without a cross-pocket import, and a WARN would
  nag every host without an authorization pocket. The README's "What is kept" paragraph names the hook instead.
- A post-erase hook (#256 option 2). It needs a repair path for a crash after commit; the pre-erase hook's
  re-run story covers the same ground with nothing irreversible done first.
- A general `IntegrityPolicy.Resolve(model)` over arbitrary unscoped rules (rev-1 shape). The only unscoped
  rule in the tree is `DefaultIntegrityPolicy`; a constructor for it is enough (backend #4).
- An `IntegrityPolicy.With(rules...)` helper. `append(policy.Rules, …)` is the composition; it is documented.
- Changes to the authentication stores, views/goth, goredis, sdk, or any migration.

## Risks

1. **#225 boot refusal is a behaviour change (R-1).** A host that boots today with an unscoped rule against
   a model where some type with relations does not declare the relation will refuse to boot after a minor
   bump, including bootstrap/seeder binaries that call `authorization.New`. Who that is: (a) hosts whose
   writes to that type are already refused — the bug; (b) hosts that never write that type through the
   pocket (read-only or seeded types) and work today; (c) hosts assigning an UNDECLARED relation on a
   declared type — legal, because the compiler treats an undeclared relation as unconstrained
   (`decisions/compiler.go:231-241`, `expression.go:253-266`) — for whom the unscoped rule works today after
   they grant the anchor first. (b) and (c) are false positives; the refusal message therefore leads with
   "scope the rule explicitly" (explicit rules are never refused), and the upgrade note says "boot staging
   first". Hosts known to the owner are safe: production-baseline's only type declares `owner`; auth-cms and
   gps-three-sixty use explicit rules. The mutations-level contract (`plan_test.go:104-135`) is unchanged;
   the pocket-level test `constructor_test.go:319-357` changes (two cases) — see PR-1.
2. **#224 pool stop.** After the one ERROR the relay returns `workers.ErrPoolShutdown`; the pool stops every
   worker and `Run` returns the cause (`pool.go:188-240`). gps-three-sixty's `relayDone` fires early and the
   host logs the error after the server drains (`main.go:375-379`), which is correct. A host that rebuilds
   the pool on a non-nil `Run` would loop (the `detached` flag is sticky); the README says restart the
   process, not the pool, and shows the `errors.Is(relayErr, tuplecache.ErrSourceIdentity)` exit recipe.
   Every replica detaches on its next poll after a recreate: a readiness probe wired to `Detached` would
   pull the whole fleet; the README names which probe gets what (Design #224.4).
3. **#256 half-finished erase states.** The hook and the store are two transactions. The plan names every
   partial state and its repair (re-run); none loses data; two leave roles revoked on a user who still
   authenticates until the operator re-runs, and one of those (a claim-blocked erase) is invisible except
   for the WARN the service now logs and the audit rows. The S4d3 `config.go`/`constructor.go` edits touch
   the same files as PR-4: PR-4 branches from `main` after v0.35.0 merges.

## Design

### #225 — a model-derived default policy and an unscoped-rule boot refusal (PR-1)

Why the two validators disagree: `validateIntegrityModel` (`integrity.go:33-60`) iterates modelled types and
`continue`s when `AllowedSubjects(rt, relation)` is empty (:43-45), so a type that does not declare the
relation is silently out of the rule; `ValidateState` (`policy.go:67-102`) iterates rules and matches on
`ResourceType` only (:88-90), so the same type is in. The store, not the service, holds the policy
(`pgx/postgres.go:100-102`, `turso/turso.go:78-80`, `memory/mutations.go:36-38`) and enforces it inside its
write boundary (`plan.go:52`, `pgx/writes.go:174`, `turso/writes.go:186`, `memory/audit.go:210`), and the store
never sees the model. The only place both exist is the composition root.

Chosen shape:

1. **`func DefaultIntegrityPolicyFor(model decisions.Model) IntegrityPolicy`** in
   `logic/mutations/policy.go`, next to `DefaultIntegrityPolicy` (:28-32). One explicit rule
   `{T, "owner", 1}` per modelled type whose `Relations` map declares `owner`, in `slices.Sorted` type order
   (cosmetic: `MinDirectSubjects` takes the max, :37-55, so order carries no semantics and no test pins it).
   No error return. A model with no `ResourceTypes` returns an empty policy. Unmodelled (opaque) types and
   types with permissions only (role-only `Role("owner")`) are NOT covered — the unscoped default covered
   them; the doc comment names both drops and says "add an explicit rule for each". Composition is
   `p := DefaultIntegrityPolicyFor(model); p.Rules = append(p.Rules, …)`.
   `DefaultIntegrityPolicy()` stays, documented as unscoped: "assumes every modelled type declares `owner`;
   beside a model that has a type without it, `New` refuses — use `DefaultIntegrityPolicyFor`".
2. **Boot refusal in `authorization.New`** (`constructor.go`, a `refuseUnscopedIntegrity(model, repo)`
   beside `warnIntegrity` :256-284, which already holds the compiled model and `repo.IntegrityPolicy()`):
   when a model is configured and `Repositories.Mutations` is wired, for each rule with an empty
   `ResourceType`, collect every modelled type that declares at least one relation and does not declare
   `rule.Relation` (this includes "declared nowhere" — the gps-three-sixty case). If any: return
   `ErrIntegrityRuleUnscoped` (new var in `config.go:22-32`, wraps `sdk.ErrInvalidInput`):
   `authorization: integrity rule {owner} names no resource type and platform declares no owner relation, so every write there would be refused; scope the rule to the types that have it, or build it from the model with mutations.DefaultIntegrityPolicyFor(model)`.
   Every mode (configuration validity, like `ErrInvalidIntegrityPolicy`). Types with zero relations are
   exempt (nothing can be written on them). `validateIntegrityModel` is untouched.
3. **`warnIntegrity` text** (`constructor.go:282`) currently recommends plain `DefaultIntegrityPolicy()`,
   which the refusal rejects on a mixed model; it now recommends `DefaultIntegrityPolicyFor(model)` or a
   per-type rule, and `integrityPolicyFixHint` (`constructor_test.go:291`) asserts the new hint.
4. **production-baseline** `cmd/server/main.go:196` switches to `DefaultIntegrityPolicyFor(accessModel())`
   (behaviour-neutral: its only type declares `owner`; it is the line hosts copy — R-7). `cmd/bootstrap/main.go:92`
   stays: it has no model ("the server's resource model is not needed here", :91-110), so there is no
   refusal there and nothing to resolve. auth-cms keeps its explicit rule; its comment at
   `authorization.go:70-80` gains one sentence pointing at `DefaultIntegrityPolicyFor`.

Rejected: resolving inside the store (no model there, and it must not grow one); a `BindIntegrity` mutator on
the repository (post-construction mutation of a value every facade already copied); inferring applicability
from the facts in `ValidateState` (a removed last owner and a type without `owner` look identical); a
refusal inside `mutations.NewService` (breaks `plan_test.go:104-135` and still would not fire where `owner`
is declared nowhere); the rev-1 general `Resolve` with explicit-rule validation (it rejected a legal explicit
rule for an undeclared relation and bought an ordering contract nothing needs).

### #224 — a distinct identity error and a relay that stops (PR-2 core, PR-3 stores)

Facts: the binding hashes the identity captured at boot (`pgx/tuple_cache.go:84-92`); `readReceipt`
(:231-256) folds "row count ≠ 1", "wrong slot/protocol", "malformed identity" and "identity changed since
boot" into one bare `ErrUnavailable` (:245-247, :252-254), and pgx `Acknowledge` (`tuple_source.go:146-155`)
never calls it: the identity sits in its `UPDATE … WHERE`, so a mid-poll identity change surfaces as
`ErrConflict`. turso's `readHead` (`turso/tuple_cache.go:84-110`) returns `ErrBinding` (wraps
`sdk.ErrInvalidInput`, not `ErrUnavailable`) for the same condition (:108-110) and runs again at
acknowledgement (:262) — two parity gaps. The pool logs any non-`ErrNoWork` error at ERROR every iteration
(`pool.go:299-304`); `ErrPoolShutdown` logs one ERROR "worker requesting pool shutdown", stops the pool and
makes `Run` return the cause (:288-291, :188-240); `ErrWorkerShutdown` ends one worker at INFO and `Run`
returns nil. A new identity is a new binding; this process can never publish again: terminal until restart.

Core (PR-2):

1. `tuplecache.ErrSourceIdentity = fmt.Errorf("tuple cache source identity changed since this process started (the database was recreated or repointed); restart the process: %w", ErrUnavailable)`
   in the var block (`tuplecache.go:14-20`). `errors.Is(_, ErrUnavailable)` callers are unaffected.
2. Runtime detach (`runtime.go`): a `detached atomic.Bool` on `TupleCache` (:74-88). In `poll`'s deferred
   failure handler (:206-225, which runs while the gate is still held — defers are LIFO), when
   `errors.Is(err, ErrSourceIdentity)` at ANY stage (snapshot or acknowledgement): set `detached`, clear
   `ready`, and — for `Poll` only, not `Rebuild` — rewrite the named return as
   `fmt.Errorf("%w: %w", workers.ErrPoolShutdown, err)`. At the top of `poll` (after the `closed` check
   :191-193, before the gate so detached calls are neither counted nor stamped): a detached `Poll` returns
   the same wrapped error; a detached `Rebuild` returns `ErrSourceIdentity` plain (`Rebuild` is a host API,
   not a `WorkFunc`; it must not leak the pool protocol). Net effect under `workers.Pool`: ONE ERROR line
   (`worker requesting pool shutdown` with the cause and the fix in `error`), one INFO `worker pool stopped`,
   `Run` returns an error with `errors.Is(_, ErrSourceIdentity)`, the host logs it once more at its own
   level. `Run`/`attempt` (:346-395) need no change: `ready` is false, every read falls back to SQL, `Fallbacks`
   counts it; the fallback `ReadSnapshot` never checks identity. `Notify`, `Close`, the scheduled-rebuild
   backoff: no interaction (backend #9). `PollFailures` counts the one failing poll; the pool's own
   `Stats().Errors` shows 1.
3. `Stats.Detached bool` (:64-70, :156-174). `LastPoll.FailureStage` already names the stage.
4. README "Optional TupleCache" (the `Stats`/alerting paragraph near :1169-1176) and the docs-site page
   (`docs/pockets/authorization.md:298-330`): one paragraph on what a recreated database looks like in the
   log, that the pool stops, restart as the fix, and the two probe shapes: **readiness keeps checking the
   database only**, with `Detached` reported in the 200 body (`"tuple_cache":"detached"`) for alerting —
   never a 503, or a recreate pulls every replica; **liveness** may answer 503 on `Detached`, or the host
   exits when `errors.Is(relayErr, tuplecache.ErrSourceIdentity)`, so the orchestrator restarts it. A missing
   `WithHeartbeat` line after the stop is the free alert. "Do not rebuild the pool: the flag is sticky."

Stores (PR-3, after the v0.34.0 tag):

5. pgx `readReceipt`: split the compound condition, keeping today's short-circuit order (count/slot/protocol,
   then hex format, then identity), so a garbage identity is never reported as "changed". Identity mismatch
   → `ErrSourceIdentity`. The others keep `ErrUnavailable` with a message each and never echo the value:
   head row count ≠ 1 → "tuple cache head row missing or duplicated (apply the tuple cache migration once)";
   wrong slot/protocol → "tuple cache head row has slot %d protocol %d, want 1/2"; malformed identity →
   "tuple cache head identity is not 32 lowercase hex".
6. pgx `Acknowledge` (`tuple_source.go:149-155`): on `RowsAffected() != 1`, call `s.readReceipt(ctx, tx)`
   and return its error when non-nil, else `ErrConflict`. One extra query on the failure path only; the
   detach then fires in the same poll on both stores.
7. turso `readHead:108-110`: binding mismatch → `ErrSourceIdentity` (a behaviour change from `ErrBinding`,
   the sdk kind moves from `ErrInvalidInput` to `ErrUnavailable`; recorded; no test asserts `ErrBinding` on
   the source path — the `ErrBinding` assertions are all mirror cases). The other bare returns get messages
   as on pgx. turso has no malformed-binding case (the column CHECK at `0002:7` forbids it).

Rejected: `workers.ConsecutiveErrorShutdown(n)` in the host (it would also stop the relay on a transient
Redis outage); returning `ErrNoWork` on repeats (lies to the pool's stats); `ErrWorkerShutdown` (`Run`
returns nil, so a supervisor cannot tell "identity lost" from a clean drain — R-2 (b)); a logger in
`tuplecache`; an sdk-level dampener (out of scope).

### #256 — `BeforeErase` (PR-4)

Facts: `EraseUser` (`useradmin.go:268-307`) checks the port, the directory, the id and self-erase (:269-280),
reads the magic-link subject keys (:281-284), prepares the `user_erased` event (:285-290), then runs the
store's one transaction detached from the request context under `EraseTimeout` (:291-293). The accepting-claim
check and the unknown-id `ErrNotFound` live INSIDE that transaction (`user/erase.go:26-51`); a repeat is
`Changed:false`. The route (`inbound/http/useradmin.go:335-352`) maps errors by sdk kind through
`web.RespondJSONDomainError`; a `sdk.ErrConflict` kind renders as the generic `conflict` code
(`sdk/pkg/web/errors.go:318-319`). `authlogic.Principal` is `type Principal = sdk.Principal` (`machine.go:89`).
`AdministrationConfig` (`config.go:1018-1117`) already carries `UserErasureRoute` (:1069-1076); `New` validates
its wiring at `constructor.go:169-171` and passes config into `authlogic` options at :587+ and transport
options at :695-712. Authorization commands refuse an ambient transaction of their own `*DB`
(`mutations/mutation.go:17`, `ErrMutationInsideTransaction`) and a recording store needs an `audit.Source`
with exactly one actor or system (`audit.go:42-46`, `pgx/writes.go:76-80`).

1. Logic (`logic/authentication`): `type EraseHook func(ctx context.Context, actor sdk.Principal, userID string) error`
   (after the file's vars; written with `sdk.Principal` so a host-pocket function needs no import of the
   authentication pocket; an unnamed func is assignable). `type ErasureConfig struct{ BeforeErase EraseHook }`
   and `func WithErasure(ErasureConfig) Option` in `options.go`; a `beforeErase EraseHook` field beside
   `userErasure` (`service.go:362-368`, :516).
   `var ErrEraseRefusedByHook = errors.New("auth: erase refused by the host's BeforeErase hook")` — no sdk
   kind of its own; the host error's kind governs the status.
2. `EraseUser` order becomes: port/directory/id/self checks (unchanged) → **`BeforeErase(hookCtx, actor, id)`**
   with `hookCtx, cancel := context.WithTimeout(ctx, EraseTimeout)` over the REQUEST context (cancellable:
   a dropped request stops the hook; nothing irreversible has happened; the bound keeps a large N from
   running past the server's own timeouts) → on error: WARN `auth: erase refused by BeforeErase`
   (`user_id`, `actor_id`, the sdk kind only — never the message, nothing from the hook) and return
   `fmt.Errorf("%w: %w", ErrEraseRefusedByHook, err)` (both `errors.Is` hold; `ErrInvariantBlocked` →
   `sdk.ErrConflict` → 409; `sdk.ErrForbidden` → 403; `sdk.ErrInvalidInput` → 400; an unkinded error → 500;
   all fail closed) → subject keys → event → store transaction (unchanged). When the store refuses AFTER a
   successful hook (claim held, unknown id), WARN `auth: erase refused after BeforeErase ran` with the same
   fields, so state (b) is visible in the log. The hook runs on every call, the repeat included: that is what
   makes a re-run complete a half-finished erase and what makes "erase again" the orphan sweep.
3. Root: `AdministrationConfig.BeforeErase authlogic.EraseHook` (doc below), the mirror field in the flat
   config, copied in `WithAdministration` (:1124-1126), passed as
   `authlogic.WithErasure(authlogic.ErasureConfig{BeforeErase: cfg.BeforeErase})`. Contradictory wiring
   refused at `constructor.go:169-171`: `BeforeErase != nil && nilDependency(repos.UserErasure)` →
   `ErrBeforeEraseWithoutErasure` (the `HTMLPolicy`-without-`Views` posture; R-4).
4. The route is unchanged; the service wraps, the route maps by kind. A claim refusal and a hook refusal
   both render as `conflict`; a host that wants its page to tell "last admin" from "claim held" returns a
   `web.SafeDomainError`-shaped error from its hook (documented, not built).
5. **Ordering and the idempotent-repair story** (the field doc, the README "Erasure" section as a paragraph
   BEFORE the numbered list, and the docs-site page):
   - Order: pocket checks → hook (authorization store, its own transactions) → authentication erase
     transaction. Never atomic across the two; the hook runs first because its work is reversible and the
     erase is not.
   - Hook contract: idempotent (revoking nothing is success); every scope (global roles included); stamps
     the administrator as the audit actor with the action as reason
     (`audit.WithSource(ctx, audit.Source{ActorType: actor.Type, ActorID: actor.ID, Reason: "user_erase"})`
     — the reason names the request, not an outcome that may not happen); attempts integrity-protected
     relations FIRST (owner, admin), so a last-anchor refusal fires before lesser roles are stripped;
     re-reads the first page until it is empty rather than walking a cursor over rows it is deleting; stops
     at the first error and returns the pocket error unwrapped so its kind maps; never runs inside the
     host's own `Transact` on the authorization `*DB` (`ErrMutationInsideTransaction`); bounded by
     `EraseTimeout` — page in batches and re-run to finish.
   - States and repair: (a) hook fails part-way → 4xx/5xx, user untouched, the roles before the refusal
     gone (guarded-first keeps this to none when the refusal is the anchor); re-run. (b) hook ok, erase
     refused by `ErrEraseBlockedByClaim` (409) → tuples gone, user active, one WARN; settle the claim,
     re-run (hook no-op, erase proceeds). (c) hook ok, process dies before commit → as (b) without the WARN.
     (d) hook ok, erase committed → done; a re-run is `changed:false` after a no-op hook. (e) a grant races
     in after the hook → an orphan tuple on an erased user, who can no longer authenticate; re-running
     erase IS the sweep (the hook runs on repeats). (f) unknown or malformed id → the hook runs first: an
     unknown well-formed id is a no-op then `ErrNotFound` (404); a malformed id is refused by the
     authorization pocket's principal validation (400) before the store would answer.
   - Integrity rules still apply inside the hook: erasing the last `platform:global#admin` is refused by the
     host's rule as 409 with nothing erased — the failure mode every example demonstrates.

## Notes

- Why the policy is built host-side: the policy lives in the store and is enforced in the store's write
  boundary; the model lives in the pocket. The only place both exist is the composition root. The boot
  refusal is the safety net for a host that keeps the unscoped default.
- Why not fix `validateIntegrityModel` instead: `plan_test.go:104-135` pins two contracts — an unscoped rule
  for a label the model never declares is accepted, and `DefaultIntegrityPolicy()` beside `doc{owner}` +
  `group{member}` is accepted. Any refusal there breaks one of them; and in gps-three-sixty's model `owner`
  is declared nowhere, so a "declared on some, absent on others" rule would never fire.
- Why the relay stops instead of throttling: a new identity is a new binding; this process can never publish
  again. One ERROR with the fix, the pool stopping, and `Run` returning the cause is the honest signal;
  `Stats().Detached` is the machine-readable one.
- The host's two databases: gps-three-sixty runs both pockets on `iamDB`, so "two databases" there means
  two stores and two transactions on one database; the ordering and repair story is the same either way,
  and the "never inside a host `Transact` on `iamDB`" line matters there.
- `workers.ConsecutiveErrorShutdown` already exists for hosts that want a worker to stop after N errors of
  any kind; it is not the answer here because a transient Redis outage would also stop the relay.
